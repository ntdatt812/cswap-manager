# Architecture and decisions

## Layout
```
src/
  extension.ts                 activation, command registration (VS Code layer)
  vscode/                      configuration, logger, localized messages
  core/                        no `vscode` import (enforced by ESLint); unit-tested in plain Node
    cli/
      processRunner.ts         spawn wrapper: shell:false, timeout, stdout bound, cancellation
      executableResolver.ts    setting → absolute PATH entries → ~/.local/bin
      cswapCli.ts              adapter: list/status/switch, auto, config, management, map, add, transfer
      transfer.ts              export / import / import-usage arguments and stderr summaries
      cliErrors.ts, version.ts
    model/                     tolerant parsers, normalized types, list/status reconciliation
    service/refreshService.ts  cache, single-flight refresh, stale tracking, events
    diagnostics/               structured, redacted diagnostics report
    security/redact.ts         redaction of emails, UUIDs, tokens, home paths, ANSI
test/
  unit/                        node:test suites (npm test)
  live/                        opt-in read-only smoke test against the real CLI (npm run test:live)
  fixtures/                    redacted JSON shaped like observed CLI output (fake identities)
```

## Process execution
- `child_process.spawn` with an argument array, `shell: false`, `windowsHide`, `stdin` ignored, a fixed working directory (the user's home, never a workspace folder), a timeout and a stdout byte limit (stderr capped at 64 KB).
- The adapter can only send three constant argument vectors (`COMMAND_ARGS`). Phase 1 runs no mutating command.
- On timeout, cancellation or output overflow the promise settles immediately and the process is killed best-effort; it does not wait for `close`, because a grandchild holding the pipes could otherwise hang it (covered by a test).
- Env adds `NO_COLOR=1` and `PYTHONIOENCODING=utf-8` (inert hints for clean UTF-8 output from the Python-based CLI).
- Windows: only `.exe`/`.com` are executed. `.cmd`/`.bat`/`.ps1` shims are reported as unsupported instead of being run through `cmd.exe`, because that would reintroduce shell parsing.

## Executable resolution
1. `cswapManager.cliPath` (declared `scope: machine`, read from the global/user value only). If set but unusable, resolution fails — it never silently falls back.
2. Absolute `PATH` entries only (relative/empty entries are skipped so a workspace cannot shadow the CLI), and none inside an open workspace folder (`searchPathEntries`): VS Code started from a shell with `<project>/.venv/bin` on PATH cannot hand the project's own `cswap` (or `uv`, `pipx`, … to the installer) to the extension. Folders are compared normalized, with a trailing separator (`/a/b` does not hold `/a/bc`), case-insensitively on Windows and macOS. A workspace folder that holds the home folder (home itself, a parent, a root) is not used, since it would hide the user's own `~/.local/bin`. `extension.ts` reads `workspace.workspaceFolders` on every lookup and invalidates the cached resolution when folders change. Symlinked folder paths are not resolved (`realpath`) for this comparison.
3. `~/.local/bin` (uv tool / pipx default).
Successful resolutions are cached until the setting changes, the workspace folders change or a spawn reports `ENOENT`; failures are not cached. Windows app execution aliases are never accepted for cswap (see *Installing cswap*).

## Data model and parsing
- Every field except the slot (`number`) is optional; `undefined` means "the CLI did not provide it".
- Usage windows are any object under `usage` that has `pct` or `resetsAt`, kept in CLI order under their own key — no hard-coded `sevenDay`/`fiveHour`. `scoped[]` entries need a `name`.
- Wrongly typed values are dropped with a warning (`code` + JSON path, never the value). Unknown fields are ignored.
- `schemaVersion` other than 1 is parsed best-effort with a `schema-version-untested` warning; missing `accounts` array is a hard `unexpected-shape` error.
- Accounts are sorted by slot; accounts without a valid slot or with duplicate slots are skipped with warnings.

## Refresh and reconciliation
- `list --json` is the primary snapshot. `status --json` is called only when the caller asks for verification (post-switch, later phases) or when the list is ambiguous (missing `activeAccountNumber`, or flags disagree with it).
- Status data is merged into a list account only when slot matches and emails do not contradict; its usage replaces the list usage only if `usageFetchedAt` is newer. Plan data always comes from `list`.
- On conflicting sources the active slot is taken from `status` only if its identity is confirmed; otherwise it is reported as unknown with `consistency: conflict`.
- Concurrent refreshes share one CLI run. `requireFresh` queues a single follow-up run instead of reusing an in-flight result; a request that arrives just after a run ends, before its follow-up has started, joins that follow-up. After `dispose()` nothing counts as refreshing (a cancelled run never reports back). `whenIdle()` resolves once no run is under way or queued, without starting one.

## Data states (for the UI phases)
| State | Meaning |
|---|---|
| unknown | the CLI omitted the field — render as unknown, never as 0/false |
| unavailable | the CLI reports a `usageStatus` other than `ok`, or no usage for the account |
| stale | a last-good snapshot exists but the latest refresh failed (`refresh-failed`) or it is older than 5 minutes (`too-old`) |
| none / error | no data has ever loaded; show the error with guidance, not an empty list |

## Sidebar (Phase 2)
- Activity Bar container **Cswap Manager** with the **Accounts** tree (`src/vscode/accountsView.ts`, `accountsTreeProvider.ts`).
- The tree model is built in `src/core/presentation/accountTree.ts` as plain data (`NodeModel`) with an injected translator, so it is unit-tested without VS Code; the VS Code layer only maps it to `TreeItem`s.
- Account row: `slot · email`, description `Active · plan · <window> <pct> … · ↻ <time to first reset>`; icon shows active (`pass-filled`, coloured by usage level) or the worst usage level. The active account is expanded by default; order stays by slot unless the user picks another sort.
- Children: one row per usage window and per scope (text bar, %, live countdown computed from `resetsAt`, never a negative countdown), then plan, login expiry, usage age and organization when supplied. Pace/forecast fields appear in tooltips only when the CLI provides them.
- Tooltips are untrusted `MarkdownString`s; CLI strings go through `appendText` (escaped), so account data cannot inject links or commands.
- View states use the `cswapManager.viewState` context key and `viewsWelcome`: loading, notFound, invalidSetting, unsupportedExecutable, error, empty, filteredEmpty. With data present, the view description shows `Stale` / active slot / age and `TreeView.message` explains stale data, refresh failures, list/status conflicts, an unmanaged login, untested schema versions and the active filter.
- Refresh triggers: activation/first show, the `RefreshScheduler` (default 120 s, `0` = off, minimum 30 s) which only runs while the view is visible **and** the window is focused and is due one interval after the last attempt of any kind, toolbar/command refresh, and `cliPath` changes. Relative times re-render every 30 s without calling the CLI. A view progress bar shows while a refresh runs.
- Stale threshold: `max(5 min, 2 × refresh interval)`.
- Filter (in-memory, per window) matches slot, email, organization, plan and usage status; sort order is the `cswapManager.sidebar.sortOrder` setting. Warning/critical colours use display-only thresholds (80/95 by default).

## Switching, status bar and quick switch (Phase 3)
- `CswapCli.switch(target)` builds arguments only from a validated integer slot or one of the two known strategies (`switchArgs`); emails/aliases are never passed and `--force` is never used. A switch gets a timeout of at least 120 s and is not cancellable, so a credential rewrite is never killed half-way. A non-zero exit with the CLI's JSON error envelope becomes `cli-reported-error` (type kept, message redacted).
- `SwitchService` allows one switch at a time (`busy` otherwise) and **always** follows it — even after a failure — with a `requireFresh` + `verifyActive` refresh. The outcome carries a verification: `confirmed` only when list and status agree on the expected slot; `mismatch` or `unverified` otherwise. The UI says "switched" only for `confirmed`.
- Quick switch (`Cswap: Switch Account…`, status bar click, view toolbar): strategies first, then accounts in slot order, searchable by slot, alias, email, plan and usage text. Picking the active account does nothing. A modal confirmation precedes every switch (`cswapManager.confirmSwitch`, default on). Account rows in the tree have an inline "Switch to This Account" action.
- Status bar (`cswapManager.statusBar.mode`: `slotUsage` default, `slot`, `nameUsage`, `hidden`): level icon + warning/error background, `$(history)` when stale, spinner while switching; at most two windows are shown, otherwise the fullest. Account text is sanitized so it cannot inject `$(icon)` syntax; the tooltip is an untrusted Markdown summary.
- `AutoRefreshController` runs the scheduler while any consumer (Accounts view visible, status bar shown) needs data and the window is focused. The extension activates `onStartupFinished` so the status bar is available without opening the view.
- Countdown to the next automatic refresh: the scheduler's `nextRefreshAt()` is the single source (`onDidChangeSchedule` fires only when it changes), and one 1 s `onCountdownTick` runs only while a refresh is due. `countdownDue` (core) decides when a countdown shows anywhere: never on stale data or while a refresh runs. The sidebar re-renders only its header per tick (while visible), the status bar only its text; the dashboard webview runs its own 1 s timer only while its model carries `nextRefreshAt`.

## Dashboard redesign (0.6.0)
- `dashboardInsights.ts` (pure, unit-tested) builds suggestions, quota left and the reset timeline from the snapshot. Rules use only CLI facts (usage, thresholds, reset times, login expiry): switch when the active account is at the warning/critical line (to the usable account with the most left), "use before reset" for another usable account with ≥25% left resetting within 3 days and before the active one, "no other account can help" with the first reset, re-login due within cswap's 7-day window. Nothing is projected.
- Quota left = sum of `100 − fullest window %` over accounts in rotation with known usage, shown in full accounts.
- Collapsible detail sections carry a stable `key`; the webview remembers which are open in its state, so the 30-second re-render does not fold them back.
- New webview message `openAutoSwitch` (allow-listed); `openSettings` now opens Quick Settings.

## Dashboard and account detail (Phase 4)
- `Cswap: Open Dashboard` (view toolbar, palette) opens one editor-tab webview inside VS Code; `Show Account Details` on a tree row opens it focused on that slot.
- **The host builds everything.** `core/presentation/dashboard.ts` turns the snapshot into a `DashboardModel` (localized strings, levels, tones, facts) defined in `src/shared/dashboardProtocol.ts`, which has no imports so the webview can share it. The webview (`src/webview/dashboard.ts`, bundled to `dist/webview/dashboard.js`) only renders it.
- **Webview security:** CSP `default-src 'none'`, nonce'd script only, styles/images/fonts from `webview.cspSource`; `localResourceRoots` limited to `dist/webview` and `media`; `enableCommandUris: false`. Rendering uses DOM APIs and `textContent` exclusively (no `innerHTML`), so CLI data cannot inject markup. Bar widths are set through CSSOM, which CSP does not block.
- **Message bridge:** webview → host messages pass `parseWebviewMessage`, an allow-list of `ready`, `refresh`, `switchToAccount{slot:int}`, `switchStrategy{best|next-available}`, `openSettings`, `showDiagnostics`. The host also rejects a switch for a slot not in the current snapshot. Switches reuse the Phase 3 flow (confirmation, single-flight, verification). The webview can never name a command.
- **UI:** summary cards (accounts, active, usage levels, data freshness), a searchable table with sortable column headers (`aria-sort`, missing values last), and a detail pane: header + badges + switch action, usage meters (`role="meter"`, value text includes the reset), pace/forecast and spend facts only when supplied, last-known usage clearly labelled as not current, fetch error/retry, plan, account (alias, rotation, per-account threshold) and freshness. Theme colours come only from VS Code CSS variables; forced-colors mode is handled; the layout collapses to one column below 900 px. Keyboard focus is preserved across re-renders.
- The panel counts as an auto-refresh consumer while visible and re-posts state every 30 s for relative times. UI state (selection, search, sort) is kept with `setState`; `retainContextWhenHidden` is off.
- A visual check was done once in light/dark themes and at 560 px width by loading the built `dashboard.js` + CSS in a temporary local page with stubbed VS Code theme variables (removed afterwards). It found and fixed a CSS ordering bug (status/note tone colours) and a focus-loss bug.

## Account management (Phase 5)
- Operations: disable/enable in rotation, set/clear the per-account switch threshold, move to a slot (swaps when occupied). Each was verified against the CLI first (docs/CLI-CONTRACT.md, Phase 5). Set/remove alias shipped until 0.9.0 and was then removed at the user's request: display names cover naming, and an alias set in a terminal is still shown and searchable.
- `CswapCli.manage(op)` builds arguments only from a positive integer slot, a threshold within 50–99.9 (`core/model/accountPolicy.ts` mirrors cswap's validator) or a priority within 0–1000, so no value can start with `-` and become a flag. These commands print text only, so success means exit 0; failures carry cswap's redacted `Error:` line.
- `ManagementService` checks the account exists, runs the command, always refreshes, and verifies the effect on the **same account** (followed by email + organization) in the fresh `list --json` — `confirmed`, `mismatch` or `unverified` are reported as such.
- `OperationGate` is shared by switching and management, so no two cswap mutations ever overlap; the dashboard disables its buttons while the gate is busy.
- UI: tree row context menu (actions shown only when they apply, via `contextValue` flags such as `cswap.account:inactive:enabled:nothreshold`), `Cswap: Manage Account…` in the palette, and action buttons in the dashboard detail (`manageAccount` message, allow-listed action + known slot). Values are always typed into VS Code input boxes with live validation, never into the webview.
- Confirmations: modal for disabling (explains rotation, warns if it is the active account or the last one in rotation) and for moving (shows which account trades places and that numeric shortcuts change meaning). Enable and threshold changes are reversible and not modal. The threshold prompt states that it changes cswap's auto-switch behaviour, unlike the display-only colour thresholds.

## Security review (Phase 6, 2026-11-24)
An independent read-only review covered process execution, executable resolution, the webview, UI text injection, secret/PII handling, state-changing operations, the test API and the packaged dependency surface. Overall risk: **low** (0 critical/high/medium, 4 low, 6 info). Fixed:
- **L1** CLI-derived text (error types, switch reasons, account names) could form `[label](command:…)` links in notifications. All such text now goes through `neutralizeLinks`; error types must look like class names and reasons like kebab-case codes, otherwise they are not shown.
- **L2** A workspace could disable switch confirmation. `cswapManager.confirmSwitch` is now `application`-scoped, read from user settings only, and listed in `restrictedConfigurations`.
- **L3** Usage text in the status bar is sanitized against `$(icon)` injection.
- **L4** Slot-addressed operations are refused (`account-changed`) if, after a fresh re-read just before running, the slot(s) no longer hold the account(s) the user confirmed.
- **I2/I3/I5/I6** base64 secrets and profile names with spaces are redacted; `ELECTRON_RUN_AS_NODE` is not passed to the CLI; JSON recovery is capped at 5 attempts; the webview CSP adds `base-uri 'none'` and `form-action 'none'`.
Accepted: reversible actions (enable, clear threshold) run without a modal; absolute PATH entries are trusted as the user's shell trusts them. Dev-only dependencies (mocha, @vscode/test-cli, vsce) have 9 audit advisories (1 high in `serialize-javascript` via mocha) with no fix available; none of them ship in the VSIX, whose runtime dependency count is zero.

## Release validation (Phase 6)
`npm run package:vsix` produces `cswap-manager-<version>.vsix` (10 files, ~42 KB: bundled `dist/`, `media/`, `resources/`, README, CHANGELOG, manifest). The archive was scanned for usernames, local paths, emails and source maps (none), installed into an isolated VS Code profile, and the extension-host suite was run against the minified production bundle.

## Diagnostics
`Cswap: Show Diagnostics` runs only the three read-only probes and renders counts, keys, codes, exit codes and timings into an untitled Markdown document, with an optional copy-to-clipboard. Paths are shown relative to `~`; emails, organization names, UUIDs, scope names and raw output are never included, and the final text is redacted again.

## Decisions
- **TypeScript 5.9**: TS 7.0 (latest) is not yet supported by typescript-eslint (`<6.1.0`).
- **node:test** for unit tests (no VS Code needed). Extension-host tests use `@vscode/test-cli` (mocha, `tdd` UI) and can run against a local VS Code via `VSCODE_EXECUTABLE`; `activate()` returns a small test API only in `ExtensionMode.Test`.
- **esbuild** bundle to `dist/extension.js`; tests are compiled separately by `tsc` to `out/`.
- **Engine `^1.90.0`** with `@types/vscode ~1.90.0`; `@types/node ~20.19` matches the oldest supported extension-host Node.

## Known limitations
- Automatic refresh pauses while the window is unfocused. Another VS Code window learns about a switch made in a window through the cross-window signal (see *Keeping windows in step*), within 5 s; a switch made in a terminal shows on its next refresh (focus or interval), unless a window running auto-switch or a refresh sees it first.
- Cross-account and strategy switches were not executed live during development; their handling is tested against fixtures derived from the CLI source.
- The dashboard does not survive a window reload (no `WebviewPanelSerializer`); reopen it with the command.
- The `spend` amounts are shown exactly as the CLI reports them (`used / limit currency`); their unit has not been verified.
- A real move/swap between two occupied slots has not been executed during development (fixture-tested only).
- The opt-in end-to-end test (`CSWAP_E2E_MUTATE=1 npm run test:integration`) sets and clears a switch threshold on an inactive slot without its own; it is skipped by default.
- Not implemented on purpose: `purge`, `unclaimed`, `tui`/`watch`, the macOS `menubar`, the `--model` switch flag (the extension sets `autoswitch.model` instead) and the API-key auto-switch option. Priority, mappings, `cswap run`, add/remove and export/import/import-usage arrived in 0.8.0; `add-token` (token on stdin only) after 0.9.0.
- Per-project accounts compare folders after resolving symlinks, junctions and substituted drives, like cswap; in a multi-root workspace Quick Settings shows the first folder's account (named). `cswap run` terminals need a trusted folder.
- The webview DOM itself has no automated tests (host-side model, protocol validation and table logic are unit-tested; the panel/message bridge is covered by extension-host tests).
- The filter is not persisted across window reloads.
- Killing a timed-out process is best-effort (`child.kill()`); a process tree is not killed explicitly.
- Alias, `fiveHour`, switch JSON output and non-`ok` `usageStatus` values have not been observed.
- Published as `nguyenthanhdat.cswap-manager` under the MIT license; the extension ID must stay stable across releases.

## Localization and picker layout (0.2.0)
- Runtime strings go through one translator (`src/vscode/l10n.ts` → `localize`, exposed to the core as the injected `t`). Bundles live in `l10n/bundle.l10n.<lang>.json` keyed by the English text, named by VS Code's locale ids (`vi`, `zh-cn`, `zh-tw`, `ja`, `ko`; `SUPPORTED_LANGUAGES` in `src/core/presentation/language.ts`, where `zh-hk`/`zh-mo`/`zh-hant` map to `zh-tw` and other Chinese locales to `zh-cn`); `cswapManager.language` (`auto` → VS Code display language) picks the bundle, independently of VS Code's own language, and a change re-renders every surface. Contributions (command titles, settings, welcome views) use `package.nls.<lang>.json`, which VS Code applies only for its own display language.
- `test/unit/l10n.test.ts` extracts every translator call with the TypeScript compiler API and fails, for every translated language, on non-literal keys, missing or stale translations, changed `{n}` placeholders, or altered `$(icon)`, `#setting#` and `command:` links (in the bundles and in `package.nls.<lang>.json`).
- Not translated on purpose: the diagnostics report (meant for support, kept in English), compact durations such as `4d 0h` (same notation as the cswap CLI), cswap's own error messages, language names (each in its own language, `LANGUAGE_INFO`), and the English word in the language row and picker title (`Ngôn ngữ · Language`, `languageTitle`), so a language picked by mistake can be undone. List and bracket punctuation in composed phrases goes through the translator (`{0}, {1}`, `{0} ({1})`).
- The Switch Account picker groups accounts (`quickSwitchGroup`): current; available sorted by highest usage ascending; at limit (critical threshold) sorted by soonest future reset; disabled or without usage last. Rows show text usage bars per window (10 cells for one window, 6 for several) and the next reset; plan, scopes and data age move to the detail line, and the subscription status is only shown when the plan has expired.

## Automatic switching (0.3.0)
- `AutoSwitchService` (core) schedules `cswap auto --once --json` every `autoswitch.intervalSeconds` (read from `cswap config`, minimum 15 s; first check 5 s after enabling). Each tick is a short process that exits by itself, so turning auto-switch off never kills cswap mid-switch. A real tick is treated as a mutation (no cancellation, ≥ 120 s timeout); a dry run as a read.
- Modes (`cswapManager.autoSwitch.mode`, `application` scope, read from user settings only, in `restrictedConfigurations`): `off` (default), `notify` (dry runs; notify once per would-be switch, with "Switch now"), `switch` (modal confirmation when turned on from the menu; after every switch a status-verified refresh confirms the new active account before the notification says so).
- Ticks run through the shared `OperationGate` (skipped while a manual switch or account change runs) and only in the window holding a `FileLease` (`globalStorage/auto-switch.lease.json`, heartbeat, stale after 3 × interval), so several VS Code windows do not all poll.
- Notices are de-duplicated: a would-be switch or "all accounts at limit" is reported once until the situation changes; errors only after 3 failed ticks in a row. Tick outcomes are logged without emails.
- Rules editor: only `autoswitch.threshold`, `weeklyThreshold`, `cooldownSeconds`, `intervalSeconds` and `strategy`, validated like cswap before `cswap config set/unset`, then re-read to confirm.
- Limitation: auto-switch only runs while VS Code is open (Windows has no cswap background service; the macOS menu bar app is out of scope).

## Quick settings and strategies (0.4.0)
- `src/vscode/quickSettings.ts` is a QuickPick over the common settings, labelled by the extension's own l10n (VS Code's Settings page only follows VS Code's display language). Row models and labels are pure (`src/core/presentation/quickSettings.ts`) and unit-tested. Toggles change in place; enum rows open a sub-picker with the current value highlighted and return to the list. Writes go to the user scope; if a workspace value still overrides a window-scoped setting, the user is told.
- `confirmSwitch` and `autoSwitch.mode` keep their user-scope-only reads; "Switch, don't ask again" writes `confirmSwitch=false` to user settings.
- Auto-switch strategies are cswap's (`cswap auto --strategy` choices, verified in the 1.2.0 source). The extension never ranks accounts for automatic switching itself; it stores `autoswitch.strategy` through `cswap config set` (verified by reading it back). The one-step "use quota before it resets" preset saves `consume-first` before turning `switch` mode on, so no tick runs with the old strategy.
- A manual one-shot `cswap auto --once --strategy …` from the switch picker was considered and left out: such a tick is subject to cswap's cooldown and thresholds, so a click would often end in "no action".
- Session impact (from cswap's source, `_print_switch_followup`): a restart is never required; Claude Code drops its cached token when the credentials file changes (next request) or after the macOS Keychain cache TTL (~30 s).

## Status bar customization (0.5.0)
- One progress bar style (`display.barStyle`) is used everywhere: sidebar rows, the switch picker and the status bar (`usageBar` in `format.ts`).
- `statusBar.mode` keeps its preset values (`slotUsage`, `slot`, `nameUsage`, `hidden`), now defined as fixed part lists; `custom` uses `statusBar.parts`. `buildStatusBarModel` renders parts in a fixed order and never produces an empty item.
- Buttons are separate status bar items right of the account and auto-switch items, shown only while the account item is (so `hidden` still hides everything). All Cswap items are created without an id (0.5.1), so they share the extension's id and appear as one "Cswap Manager" entry in the status bar's context menu. Only actions the status bar cannot otherwise reach are offered: switching is the account item's own click, and filter/sort act on the Accounts view, so they are not buttons.
- Live preview: `StatusBarController.preview()` overrides the saved look in memory while a picker is open; ending the picker (save, Back, Esc) clears it, so nothing is written until Enter.
- Navigation: every screen opened from Quick Settings has VS Code's `QuickInputButtons.Back`; Esc (or focus moving away) closes everything, because a hidden QuickPick cannot tell Esc from focus loss.

## Display names (0.7.0)
- cswap aliases are lower-case ASCII by design (`models.normalize_alias`: they are command identifiers). Free-form names live in the extension: `cswapManager.displayNames` (application scope) maps a 16-hex SHA-256 prefix of `email|organizationUuid` to a name, so names follow accounts across slot moves and settings.json holds no email.
- `RefreshService` takes a `decorate` hook that adds `displayName` to every snapshot; a settings change calls `redecorate()`, which re-applies names without running cswap. `accountName` prefers the display name, then the alias, then the email.

## Account lifecycle, per-project accounts and transfer (0.8.0)
Contracts are in `docs/CLI-CONTRACT.md`; none of these commands has JSON, so each parser accepts only the verified English lines and anything else is `unexpected-shape`.
- **Priority** (`PriorityStore`): `cswap priority` is read after the first refresh and attached to snapshots by the same `decorate` hook as display names (`applyPriorities`; the slot decides, the email cross-checks). A priority change is verified by reading the list back, and `ManagementService.onDidApply` hands that read to the store; after an add, remove or move the store re-reads; other changes (alias, threshold, rotation) cannot move tiers and read nothing. Project mappings (`cswap map`) are read on demand: when Quick Settings opens, before assigning, and fresh before opening Claude Code for a project.
- **Add / remove**: `addCurrent` runs under the operation gate and confirms that the added slot became the active one. `remove` always prompts in cswap, so it gets `y` on stdin only after the VS Code modal; `ProcessRunOptions.input` is the only way stdin is opened. Removal is offered in native UI only: the dashboard's allow-list (`ACCOUNT_ACTION_IDS`) deliberately excludes it.
- **Project accounts** (`ProjectAccounts`): `map`/`unmap` run under the gate and are verified by reading `cswap map` back; an unmap only requires the folder's own entry to be gone (a parent mapping may still apply). `cswap run` is started as a terminal whose process is cswap itself (`shellPath` = resolved executable, fixed arguments), so nothing passes through a shell and the global login is untouched.
- **Transfer** (`core/cli/transfer.ts`, `vscode/transferFlow.ts`): export, import and import-usage always get an absolute file path (`isSafePathArgument`), never `-`, so logins never pass through the extension's pipes; their summaries are read from stderr (`OutputParser` receives stderr; it is never logged raw). Export is confirmed in a modal, warns when the target is inside an open workspace folder, never uses `--full`, and the extension never opens the file. Import is confirmed, with *Replace existing* (`--force`) as a separate button; when cswap reports that the live login's slot was rewritten, the user is told that `switch --force` (which the extension never runs) activates it. *Save usage readings* writes this computer's `list --json` verbatim after checking that it parses.
- **cswap updates** (`CswapUpdateCheck`): at most one request a day to `pypi.org/pypi/claude-swap/json` (5 s timeout, 2 MB cap, final releases only), 30 s after start-up; the update runs the installer's upgrade, since `cswap upgrade` does not upgrade on Windows. Since the automatic update (after 0.10.0) it no longer types a command into a shell; see *Updating cswap* below.
- **Progress bar precision**: `blocks` uses Unicode eighths (~1% steps over 10 cells); `circles`/`squares` have halves (~5%). Unicode has only a full and an empty parallelogram, so `media/usage-bars.woff` (built by `scripts/build-usage-bar-icons.py`, proportions of Segoe UI Symbol's ▰▱) adds nine slanted cells contributed as icons `cswap-slant-0…8` (empty, eighths, full). `usageBar(…, { icons: true })` uses them where `$(icon)` renders: status bar text, quick pick labels/descriptions and tooltips. Tree item descriptions cannot render icons, so the sidebar keeps ▰▱ whole cells. The switcher's description is built display-ready in core: its few CLI-derived parts (usage status, window label) are neutralised with `sanitizeLabel` where they are joined with the bars, so the VS Code layer passes it through unchanged; tooltips enable theme icons, `appendText` then escapes `$(` in all data, and only a row's `bar` matching `SLANT_BAR_PATTERN` is appended as Markdown.

- **Drag and drop** (`AccountsDragAndDrop`): the drag carries only the slot (own MIME type) of a single account node; a drop onto another account node runs the internal, uncontributed command `cswapManager.moveAccountTo`, which re-validates both slots and runs `runDropMove`. A drop is deliberate and a swap is reversible, so there is no modal: progress shows in the view (`ProgressLocation` with the view id) and a confirmed result offers **Undo**, which swaps back through `ManagementService.apply(…, stateAfterTheMove)`, so it refuses if either slot changed meanwhile. *Move to slot…* keeps its confirmation.
- `ManagementService.apply` skips the re-read before a change under the same rule as switching (`canTrustConfirmed`: the snapshot acted on is under `CONFIRMED_FRESH_MS` = 15 s old, still the latest read, and no refresh failed since); otherwise it re-reads and refuses when a touched slot changed. Both services call the one function.
- Every terminal the extension opens (`cswap run`, the cswap install) is created by `createGuardedTerminal`, which on Windows sets `NoDefaultCurrentDirectoryInExePath=1`. The cswap update's terminal (`ProgramTerminal`, after 0.10.0) starts its program itself and sets the same variable in that program's environment.
- **Even pace**: cswap's `expectedPct` is the share of the window's time already passed. The dashboard labels it *Even pace by now* and draws it as a neutral tick on the meter bars (`Meter.pace`), explained in the bar's tooltip and accessible value.
- **Dashboard**: the active card is a two-column grid (account and switch buttons | stacked meters; one column below 620 px). Reset-timeline rows are buttons that select the account (`selectRow`), marked with `aria-pressed`.

### Independent review of the 0.8.0 batch
A read-only security review found 1 high, 1 medium, 6 low and 3 info issues; all are fixed:
- **H1** `cswap run` terminals start in the project folder and cswap finds `claude` with `shutil.which`, which on Windows searches the current folder first, so a planted `claude.cmd/.bat/.exe` would run. The terminal now requires a trusted workspace and sets `NoDefaultCurrentDirectoryInExePath=1`.
- **M2** Priorities were matched by email, but one email can own several accounts (one per organization) and `cswap priority` prints no organization. The slot now decides, the email only cross-checks it, and an ambiguous tier is unverified rather than assumed 0.
- **L3** The update terminal starts in the home folder with the same variable; `~/.local/bin` (used by both uv and pipx) is resolved by which installer's tool folder holds claude-swap.
- **L4** "(account removed)" map rows are `<path> → <email> (account removed)`; the parser and fixture now match.
- **L5** Folders are compared after `realpath` (cswap uses `Path.resolve()`); mapping changes are verified against a fresh read only.
- **L6** Quick Settings tells "not read yet" from "not assigned" and names the folder in multi-root workspaces.
- **L7** Saving usage readings warns inside a project folder and reports write errors.
- **L8** A single-account export re-checks inside the gate that the slot still holds the confirmed account.
- Info: `add` output with a move is reported as a move; the PyPI request has an overall deadline; outdated limitation notes were updated.

## Keeping windows in step (0.6.0)
- Auto-switch runs in one window, and windows only poll while focused, so other windows could show an old account. `CrossWindowSync` writes `active-account.signal.json` (slot, time, `vscode.env.sessionId`; no account data) into global storage when a fresh snapshot shows a different active slot, and watches that file; a signal from another window that disagrees with this window's slot triggers one refresh (`trigger: 'external'`). When the signal is read is decided by `SignalReadTimer` (`src/core/service/activeSignal.ts`, unit-tested with fake timers): the focused window after 300 ms; background windows at a random moment within 5 s, keeping a read already waiting when more events arrive, and reading at once when they come to the front, so one switch does not start cswap in every window at the moment Claude Code is busiest. Before deciding, the read waits for any refresh under way or queued (`RefreshService.whenIdle`), which may already show the new account. The decision logic (`ActiveSlotTracker`) only writes on a real change after the first load and ignores its own echo, so windows cannot ping-pong.
- Settings changes already reach every window through VS Code, but only windows running the same extension version understand new settings: after an update each window needs its extension host restarted.

## Auto-switch security review (0.3.1)
An independent read-only review of the 0.3.0 auto-switch code found 1 medium, 7 low and 6 info issues (no critical/high). All are fixed, each with a regression test in `test/unit/autoSwitch.test.ts`:
- **M1** A mode change while the lease file was being acquired could still start a real (non-dry-run) tick. The mode is now re-read inside the operation gate immediately before cswap starts, and only `switch` runs without `--dry-run`.
- **L1** Wrongly typed values from `cswap config` (e.g. a string interval) could produce a NaN interval: back-to-back ticks and a lease that every window treated as stale. Rule values are type-checked and the interval is clamped to 15 s – 1 h.
- **L2** An unwritable lease file caused an unhandled rejection every interval and no user-visible state. It now counts as a failed tick (reported after 3 in a row); lease release errors are ignored.
- **L3** A real switch (exit 0) without a readable `switch` event produced no notification. It is now verified and notified.
- **L4/L5** CLI error text in notifications is redacted and length-capped; the rules summary is link-neutralised and only shows cswap-style strategy codes.
- **L6** A real tick has a 10-minute safety timeout (manual switch: 2 minutes); after any real tick that does not end cleanly the state is refreshed.
- **L7** `cswapManager.autoSwitch.mode` has `ignoreSync: true`, so Settings Sync cannot turn automatic switching on on another machine.
- Info: a lease heartbeat far in the future counts as stale; a `mismatch` verification names the slot that is actually active; the rules editor compares the value it wrote with what cswap reports; the rules summary includes the check interval.
- Accepted: two windows starting at the same instant can both run one tick (write-then-verify is not a mutex); cswap's own state lock and cooldown prevent a double switch, so the cost is a duplicate poll. If VS Code exits during a real tick, the cswap process is left to finish on its own.

Quick Settings › Advanced… › **Notifications…** edits all three.

## Installing cswap (after 0.10.0)
- Offered, never silent: the `notFound` welcome view's first button, the refresh error's **Install cswap…** button, and one notification per window session the first time a refresh reports `executable-not-found` (only in the focused window; another one asks when it is focused). The notification's other button opens Quick Settings at the cswap path (`cswapManager.quickSettings` with `'cliPath'`).
- Plan (`planCswapInstall` in `src/core/cli/cswapInstall.ts`, pure): every step is `{ tool, program, args }`, where `program` is the absolute path located below (a bare or relative name makes the tool count as missing) and `args` the fixed array in `INSTALL_ARGS`. `uv` → `tool install claude-swap`; else `pipx` → `install claude-swap`; else Windows `winget` → `install --id=astral-sh.uv -e --source winget --accept-source-agreements --accept-package-agreements`, with `next: 'uv'`; else macOS `brew` → `install uv`, with `next: 'uv'`; else instructions with links to uv's installation guide and claude-swap on PyPI, and nothing runs. No argument comes from settings, paths or account data; no remote script runs.
- Detection without a shell (`locateTool`, returns an absolute path): PATH entries (absolute, outside the workspace folders), then known folders (`~/.local/bin`, `~/.cargo/bin`, winget's `Links` and `Packages\astral-sh.uv_Microsoft.Winget.Source_8wekyb3d8bbwe` folders, `WindowsApps`, Homebrew's `bin`), through the executable resolver's own `findExecutableIn` (Windows: `.exe`/`.com`). App execution aliases (`WindowsApps\winget.exe`) fail `stat` with EACCES, so `statKind` does not count them; only the winget lookup passes `allowAppAlias`, which accepts an alias (`isAppExecutionAlias`: stat fails with EACCES/UNKNOWN and lstat sees a link) whose folder is exactly `%LOCALAPPDATA%\Microsoft\WindowsApps`. cswap and the other installers never accept one.
- Running (`src/vscode/cswapInstall.ts`): the modal lists each program by its full path with its arguments (e.g. `C:\Users\…\uv.exe tool install claude-swap`; for the second step, which does not exist yet, `uv tool install claude-swap` with the uv that winget/Homebrew installs), and for winget says that it accepts the package's and the source's agreements on the user's behalf. Each step is a guarded terminal (`shellPath` = the program, `shellArgs` = the arguments, home folder as cwd, the full command line written first through `message`), so no shell looks anything up: the window's terminal environment, `terminal.integrated.env.*` or another extension's environment collection (a venv prepended to PATH), relative PATH entries or PATHEXT `.cmd`/`.ps1` cannot substitute another program. The terminal closes when its program exits (verified in the extension host: `onDidCloseTerminal` with `exitStatus` `{ code, reason: Process }`); then the next program (uv) is located again (absolute path, including winget's `Links`/`Packages` folders, which are not on this window's PATH) and started the same way. A terminal closed by the user (reason `User`/`Extension`/`Shutdown`) ends the watch. Every 5 s (for 10 minutes after a step starts) the extension invalidates the `CachedExecutableResolver` and resolves cswap again; when it is found it refreshes (`trigger: 'configuration'`, `requireFresh`) and offers **Add Account…**. When a step's program exits and neither cswap nor the next program is found, a warning gives the exit code and the command to run by name in a terminal of one's own (the output closed with the terminal), with **Choose its path…**. Timers and listeners are disposed with the extension.
- Not covered: the installers still get the terminal's environment (e.g. `UV_INDEX_URL`, `PIP_INDEX_URL` or `HOMEBREW_*` from the user's environment or a trusted workspace's `terminal.integrated.env.*`), which can change where they download from; the extension does not set `strictEnv`.

## Updating cswap (after 0.10.0)
- Decision (`decideUpdate` in `src/core/cli/cswapUpdate.ts`, pure): after a check with a newer final release, `upgrade` when `cswapManager.autoUpdateCswap` (application scope, user settings only, on) is on and the move is tested (`upgradeTested` in `src/core/cli/version.ts`: the new version's line is in `TESTED_CLI_LINES`, or it is a patch of the line in use), even for a version the user once skipped; a newer, untested line is offered instead, with a note and *Update anyway* (several commands parse cswap's text output, which a new line may change); else `offer` (*Update* / *Skip this version*) unless that version was skipped and the check was not requested. The daily check (`checkCswapUpdates`) and the `LAST_CHECK_KEY` record are unchanged; **Check for cswap Update** (`check(true)`) applies the same decision at once.
- Plan (`planCswapUpgrade`, pure apart from the injected file checks): the installer is the one whose folder holds the resolved cswap (`/uv/`, `/pipx/`), or for `~/.local/bin` the one whose tool folder holds claude-swap (`installedWith`: `UV_TOOL_DIR`, `%APPDATA%\uv\tools`, `$XDG_DATA_HOME/uv/tools`; `PIPX_HOME`, `~/pipx`, `~/.local/pipx`, `$XDG_DATA_HOME/pipx`, each `/venvs`; relative values ignored; directory existence only). That program is found with the installer's `locateTool` (absolute PATH entries outside the workspace folders, then known folders; a bare or relative result counts as not found) and started with `UPGRADE_ARGS` (`uv tool upgrade claude-swap`, `pipx upgrade claude-swap`). Ambiguous, unknown or not found → an instruction with the command by name (`upgradeCommandByName`); in automatic mode that notification also says which version is available and offers *Skip this version*.
- Running (`src/vscode/cswapUpdateCheck.ts`): `NodeProcessRunner` (`shell: false`, argument array, home folder as cwd, 5 min timeout, 1 MB stdout cap, stderr capped by the runner), environment `cliEnvironment` + `NoDefaultCurrentDirectoryInExePath=1` on Windows. Progress is `ProgressLocation.Window` (status bar). It runs inside `OperationGate.runWhenFree` (waits up to 60 s for a switch or account change, else *busy*), and inside `PausableRunner.pauseWhile` (`src/core/cli/pausableRunner.ts`), the runner every cswap command goes through: commands already running get up to 60 s to finish, new ones wait until the upgrade ends (their time limit starts then; a cancelled refresh stops waiting). On Windows a running `cswap.exe` (or its venv's Python) cannot be replaced, which is why the extension's own commands are held; `cswap run` terminals and other windows' commands cannot be, hence the hint in the failure message.
- One window at a time: `RUNNING_KEY` in `globalState` (the start time; cleared when done; ignored after 10 minutes or when dated in the future, `upgradeRunningElsewhere`) plus an in-window flag. Windows learn of each other's `globalState` writes with a short delay, so two windows starting within that delay could still both run; the daily `LAST_CHECK_KEY` makes that unlikely, and the second upgrade then finds nothing to do or fails on the lock.
- After exit 0: `resolver.invalidate()`, `cswap --version` again, `verifyUpgrade` (at least the release upgraded to; `unchanged` / `unverified` otherwise), refresh (`trigger: 'configuration'`, `requireFresh`), and *cswap was updated: A → B.* A failure (`upgradeProcessOutcome`: exit code and `redactLine(stderr, 'last')` passed through `neutralizeLinks`; timeout; output limit; not started) is a warning with **Try again** (plans again) and **Open in terminal**. The log gets the tool, exit code, duration and the redacted line only; stdout is never read.
- *Open in terminal* (`ProgramTerminal`, `src/vscode/programTerminal.ts`): a `Pseudoterminal` whose program the extension starts itself (`spawn`, `shell: false`, same program, arguments, cwd and environment, under the same gate, pause and marker). A terminal whose process is the program (`shellPath`) closes when it exits, output and all, so a quick failure could not be read; this one shows the output (at most 1 MB, not stored or logged) and stays open. Closing it stops showing output but does not kill the installer, which could leave cswap half-replaced.
- Quick Settings › Advanced… › **cswap version** (`cswapVersionText` · `cswapUpdatesLabel`: *updates automatically* / *asks before updating* / *not checked daily*) opens a screen with *Check for a cswap update now* and the two settings as on/off rows. Both keys are in `USER_SETTING_KEYS`, so an extension update that has not registered them yet asks for a reload.

## Usage history (after 0.10.0)
- Recording (`src/vscode/usageHistoryStore.ts`, setting `cswapManager.usageHistory`, application scope, on): after each refresh in the focused window (`onFocusedSnapshotChange`), one reading per account with usage and an email: `{ at, windows: {key: pct}, scoped?: {name: pct} }`, where `at` is cswap's `usageFetchedAt` (the snapshot time only while cswap calls the usage current). Accounts are keyed by `displayNameKey`; no email or other account data is stored.
- Pure model (`src/core/model/usageHistory.ts`): readings of one account closer than 30 minutes are thinned (the newest reading replaces a tail that came too soon, so points stay ≥ 30 minutes apart plus the latest); 8 days are kept; at most 3000 readings in all (oldest dropped first). The file is parsed defensively (version 1, 16-hex keys, bounded names and values); anything else is "damaged" and the history starts afresh, with a log line that carries no data. Readings dated more than an hour ahead (`HISTORY_MAX_AHEAD_MS`) are dropped both when the file is read and when a snapshot's readings are taken, so a future-dated point can neither outlive pruning nor win the cap. Series values are read with `Object.hasOwn` (`pointValue`), so a window named `constructor` never reads an inherited member.
- Storage: `usage-history.json` in `globalStorageUri`, read on first use, written at most every 10 minutes and on close (synchronously in `dispose`): the new readings are merged with the file on disk (another window may have written), written to a temporary file and renamed over it (retried briefly on Windows). A file watcher reloads it when another window writes or clears it. **Cswap: Clear Usage History** asks in a modal and deletes the file.
- Dashboard: `buildDashboardModel` gets the history through `DashboardOptions.usageHistory` (only while recording is on) and adds a **Last 7 days** section to the account detail, for the 7-day window and the limiting window (`fullestWindow`) when that is another one. `summarizeWindow` gives the readings of the last 7 days and `averagePerDay`: the rises between consecutive readings (a drop is a reset and is left out) over the measured span, only with ≥ 3 readings over ≥ 1 day; otherwise "Not enough readings yet". The webview draws an inline SVG (`createElementNS`, no HTML parsing): a polyline from the first to the last real reading (nothing extended to now or beyond), a thin baseline, `--vscode-charts-blue`, `Highlight` in forced colours.
